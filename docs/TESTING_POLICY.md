# TESTING POLICY — San Francisco 1906

**Статус:** обязательная инструкция для **любого изменения кода или игровой логики**, этап A, 25.10.2026. Она описывает проверки и отчётность, но **не меняет игровую механику**. Единственная истина о доступных командах — текущий [`package.json`](../package.json), о сценариях — каталог [`tests/`](../tests/), о CI — [`qa.yml`](../.github/workflows/qa.yml) и профильные workflow.

## Главное правило

**Прошли старые тесты ≠ новая механика проверена.** Прежде чем писать код, найти существующие тесты затронутой системы, понять их инварианты и добавить новые проверки для нового поведения. Не переделывать устоявшийся тест просто для получения зелёной галочки, если пользователь не утверждал изменение правила. Изменение теста требует объяснения, **какой прежний контракт стал неактуален и каким явным решением заменён**.

## 1. До реализации — обязательно

1. Открыть актуальные `main`, [`AGENTS.md`](../AGENTS.md), [`CORE_RULES.md`](CORE_RULES.md) и профильные записи [`DECISION_LOG.md`](DECISION_LOG.md). Уточнить статус: обсуждение, утверждённый дизайн или действующее правило.
2. Изучить **связанный исполняемый код**, а не только описание карты: источники статуса, цена/покупка, время срабатывания, сохранения, импорт, UI.
3. Открыть все релевантные существующие тесты из [`tests/`](../tests/). Найти аналогичные сценарии, конвенции подготовки state, проверку реального эффекта и варианты экрана. Проверить список запускаемых тестов в [`package.json`](../package.json) и правило обнаружения E2E в [`playwright.config.mjs`](../playwright.config.mjs).
4. Перед кодом кратко зафиксировать **инварианты, которые нельзя ломать**, и перечислить новые сценарии: обычный, отрицательный, граничный, повторное срабатывание, влияние на других игроков, сохранение/перезагрузка, мобильный UI (если затронут).
5. Проверить связанные открытые issues/PR и историю отмен: в особенности нельзя возвращать отменённые правила по аналогии со старым тестом/кодом.

## 2. Во время внедрения

- **Добавлять регрессионные тесты вместе с механикой в том же PR.** Prefer узкие unit/core проверки для формул и доступности; E2E для реального пользовательского сценария и взаимодействий.
- Проверять **фактический результат**: деньги/материалы/очки/влияние, расход действия и местоположение работника, владельца и доступности эффекта, предотвращение повторного начисления, невозможность недопустимого маршрута или постройки.
- Не ограничиваться `assert.ok(result.ok)` или существованием кнопки: тест должен ловить ошибку, ради которой он создан.
- Если правка затрагивает данные сохранений, добавить загрузку старого сохранения и запись/чтение нового, **без уничтожения прогресса**.
- Отдельно покрывать коллизии: владелец услуги = получатель награды; в районе уже есть однотипный стандартный или рыночный объект; услуга есть в соседнем районе; стройка незавершена; ресурс закончился; исключительные индикаторы риска.
- Для численных эффектов проверять условия активации, **однократность**, последовательность расчётов (начало/конец года), ограничения вместимости/границ и эффекты у сторонних игроков.
- Не менять баланс, термины, другие карты и UX по пути «ради зелёных тестов», не согласовав это.
- Изменение только документов **не требует утверждать, будто прогнаны игровые тесты**. Для таких PR достаточно проверки ссылок/согласованности; если CI запустился, сообщить его действительный статус.

## 3. Команды и обнаружение сценариев

| Команда | О чём свидетельствует успешный результат | Чего не гарантирует |
| --- | --- | --- |
| `npm run test:core` | Набор `node --test` из `package.json`: логика, правила, статические проверки и регрессии подключённых файлов | Не доказывает правильность мобильного UI или ещё не покрытого эффекта |
| `npm run test:e2e` | Playwright по [`playwright.config.mjs`](../playwright.config.mjs): все матчащие тесты в `tests/` | Не проверяет сценарий, для которого **не написан** E2E |
| `npm test` | Сначала core, затем E2E | Не заменяет проверку нового сценария и реального поведения |
| `npx playwright test tests/<имя>.e2e.spec.mjs` | Целевой E2E для изменённого модуля | Не заменяет полный прогон перед объединением |

**ВАЖНО: `test:core` в `package.json` — фиксированный список файлов, не автоматический glob.** При создании нового `tests/*.test.mjs` необходимо добавить его в команду `test:core`, иначе полный `npm test` и GitHub Actions могут пройти **без нового теста**. Проверить это перед PR.

**Текущее правило обнаружения Playwright:** `testMatch: ['**/e2e.spec.mjs', '**/*.e2e.spec.mjs']`. Новые файлы назвать соответственно; иначе они могут **не выполняться** при `npm run test:e2e`. Для браузерных тестов `playwright.config.mjs` запускает локальный веб-сервер через `python3 -m http.server 4173`; нужен установленный Chromium (`npx playwright install --with-deps chromium` в Linux CI).

**CI:** [`Prototype QA`](../.github/workflows/qa.yml) на push в `main` и PR в `main` устанавливает Node 22/Chromium и запускает core + E2E. Отдельный [`Industrial buildings regression`](../.github/workflows/industry-regression.yml) запускается **только для заданных путей PR** и не заменяет общую проверку. Перед merge проверить **успех актуальных проверок на commit HEAD**, а не зелёный статус старого коммита. Если GitHub Actions недоступен или не запустился, написать «не проверено», не «всё прошло».

## 5. Минимальные тестовые матрицы

### Новое здание/эффект
- Доступность при выполненных условиях; **недоступность** без денег, действия, местоположения, материалов, свободной площадки, соответствующего соседства или нужного объекта (по настоящему правилу).
- Аккуратный расчёт `VP/Income/Influence`/стоимости и момента срабатывания.
- Завершённая/незавершённая/перестроенная/закрытая стройка; собственность и разрешение использовать чужой эффект.
- Повторное действие/конец года не начисляют одноразовый бонус дважды.
- Копии карты, пересечение с другими зданиями, несколько игроков и границы доступных ресурсов.
- UI запускает **тот же** кодовый эффект, который проверен в unit, а не локальную «подделку» интерфейса.

### Новая логистика/ресурсы
- Физическая непрерывность маршрута, невозможный переход, закрытый парк, цена **по всем участкам**, порядок источников и разгрузок.
- Вместимость **на каждом сегменте**, дополнительные погрузки, собственный склад, конечный остаток ресурсов.
- Повторное прохождение узла, отмена до подтверждения, недостаток денег, нехватка запаса, сохранение и восстановление.
- Реальная доставка и итоговый баланс всех участников, а не только визуальное появление груза.

### Газета / институты / финальная катастрофа
- Кто и **в каком радиусе** защищён для **конкретного эффекта**; не считать строительный доступ к службе равным физической защите.
- Стандартный `std_fire` — **только свой район** в Фазе I и II; `firehouse` — другой проект. Открытый [разрыв импорта в Фазу II — issue #43](https://github.com/RumplestiltskinBiD/sf1906-prototype/issues/43).
- Порядок расчёта П, устойчивости, разрушений/пожара; нельзя дважды вычесть бонус службы или дважды списать штраф; испорченные/разрушенные объекты не должны вести себя как действующие, когда правила этого не допускают.
- Газетные события считают только актуальные условия; прогноз и финальный итог сохраняются; перезагрузка не повторяет событие.

### Мобильный UI (если меняется интерфейс)
- Обязательно два поддерживаемых сценария: **390×844** (портрет) и **932×430** (ландшафт). В существующих E2E есть примеры `page.setViewportSize` для обоих размеров.
- У доступной кнопки есть рабочее действие; видна причина недоступности; окна не перекрывают карту, рабочие и подтверждение.
- Нет неконтролируемого горизонтального скролла, пропажи важного HUD, недоступных областей нажатия.
- Проверить **весь путь действия**: открыть → выбрать объект/район/маршрут → подтвердить → увидеть реальный state → перезагрузить и сверить сохранение. Успешный статический screenshot недостаточен.

## 6. Перед объединением PR

1. Полный `npm test` **если доступны локальные браузерные зависимости**; при невозможности явно отметить, что реально выполнялось и почему. Для полного PR проверить GitHub Actions по текущему HEAD.
2. Убедиться, что профильные **новые тесты действительно участвуют в общем прогоне**, а не запущены вручную однажды или пропущены из-за `testMatch`.
3. Проверить, что тесты не были ослаблены только для прохождения.
4. Разделить **исполняемый код**, **утверждённый дизайн**, **фактическое покрытие тестами** и **ручную UX-проверку**.
5. Обновить реестр и [`PROJECT_STATUS.md`](PROJECT_STATUS.md) после code merge; не объявлять «внедрено» на этапе обсуждения и не считать документальный PR обновлением версии игры.

## 7. Формат короткого отчёта в конце внедрения

- **Что поменялось:** список реальных правил/компонентов и PR.
- **Тесты:** `core X/Y`; `E2E X/Y`; названия добавленных сценариев; отдельно **мобильные 390×844 / 932×430**.
- **CI:** успешен/неуспешен/не запускался — только после проверки актуального HEAD.
- **Не проверено / риски:** отсутствующие сценарии, открытые баги, ручные ограничения.
- **Статус:** в ветке / PR открыт / объединено с `main`.

**Запрещено:** «всё проверено», «100% тестов», «на мобильном работает», если реальные соответствующие запуски и результаты не доступны. Не придумывать число проверок.

## 8. Документационная работа — отдельный режим

Если PR меняет **только Markdown** (как Этап A), проверить целостность ссылок, имён путей и актуальность утверждений; **не требовать игрового E2E ради документа**, но также не писать, что браузерные тесты выполнены. Если CI автоматически запустился, сообщить его настоящий результат. При будущем игровом PR этот документ уже является обязательным.
