## 2. Утверждённые игровые контракты — не пересматривать молча

1. Все R01–R08 — уникальные общедоступные карты. Получение — **основное действие представителя** через предусмотренную точку: Civic Center либо готовый Политехнический кампус. Проверяется обычная достижимость представителем.
2. При взятии карта становится недоступна другим игрокам; **требования R03/R04 при получении не проверяются**. Само получение не означает финансирования, не расходует его стоимость и не включает эффект.
3. **Нет лимита количества неоплаченных карт у игрока.** Нет лимита срока хранения: можно держать любое число карт всю партию, в том числе стратегически блокируя соперников. **Нет принудительного ежегодного возврата.** Не вводить пока планшетные слоты.
4. **Финансирование — отдельное быстрое действие в свою активацию**, а не ещё одно основное действие. При финансировании проверяются принадлежность карты, деньги, остальные условия. Только после успешной оплаты спонсор получает VP/Influence, и общегородской эффект начинает действовать для всех. Каждую карту финансируют только один раз за партию.
5. R03: в момент финансирования в городе существуют **2 завершённых пожарных учреждения**, std_fire/firehouse, любых владельцев. R04: **1 завершённое медицинское учреждение**, std_clinic/clinic, любого владельца. До выполнения требований карта просто остаётся у игрока, не давая эффекта и награды.
6. **Общее worker-placement-правило:** каждое отдельное завершённое здание с **основным действием представителя** имеет **одно рабочее место на игровой год**. Первый использовавший его игрок (хозяин или гость) занимает место до следующего года; другая построенная копия — независимое место. Пассивные свойства, быстрые действия без размещения рабочего, доход и обычные грузовые доставки не блокируются. Уже имеющаяся actionSpaceOccupancy — точка интеграции; нужен аудит полноты применения.
7. **Политехнический кампус:** «Научная программа» — **одно основное получение исследования за год на экземпляр кампуса**. Если единственным посетителем стал соперник, собственник получает +$1 из банка; если собственник — выплаты нет. Посетитель не оплачивает комиссию, два посещения одного кампуса в один год невозможны.
8. **R02:** после финансирования R02 любой игрок при **завершении** здания с положительным приростом У может заплатить дополнительно $2, чтобы уменьшить именно прирост У этой постройки на 1; П не меняется, один раз на конкретную постройку. Не брать $2 при начале строительства; цена финансирования самой R02 — отдельные $4.
9. Нет специального запрета финансировать R05 в 1905 году. Последний год не вводит автоматически запрет для других исследований. Не добавлять произвольно добровольное возвращение карты: этот вариант отдельно не утверждался.
10. Соблюдать актуальные параметры, ID, эффекты и награды из research-cards.js; не переписывать утверждённый баланс ради удобства кода.

## 3. Целевая архитектура по P22

Использовать **один источник данных карт** — research-cards.js — и переиспользуемые селекторы/операции: доступные карты, принадлежность, доступность финансирования, успешное финансирование и активные общегородские исследования. Не создавать отдельный игровой движок/интерфейс для каждой карты.

- В state — **один канонический статус на ID исследования** (например, available / held by player / funded by player + round). Не хранить несколько расходящихся массивов «рынок», «рука» и «все открытые» без строгой синхронизации. UI выводится из состояния.
- Отдельно: общие **проверка действия/транзакция**, **подписанные точки эффектов** и данные карточек. Общегородские эффекты должны применяться из уже существующих расчётов (риск, цена ресурса, Income, городская цель, генерация запасов, конец Фазы II), а не из нарисованного UI.
- Добавление будущей R09: новая запись в реестре и её профильный effect handler; автоматическое появление в старых сохранениях как available; без обязательных исправлений всех экранов и случайных числовых лимитов «8 исследований».
- Не создавать универсальный event bus ради гипотетических игр. Точки расширения нужны ровно для реально существующих типов эффектов.
- При изменении state — миграция для партий до введения исследований, сохранение уникальности статусов и отсутствие повторных выдач при повторной загрузке.

## 4. Этапы реализации — по порядку

### Этап 0. Аудит и матрица зависимостей (без изменения игры)
- Сверить свежую main, AGENTS/TESTING_POLICY, issue #207, актуальные 8 карточек и тесты.
- Составить таблицу: исследование → место в game-core.js/app.js/catastrophe-core.js → исходные инварианты → позитивные и негативные тесты.
- Проинспектировать **все** основные действия, которые размещают рабочего в готовом здании, и их занятость через actionSpaceOccupancy. Отдельно отличать газетную экспедицию, которой нужна служба как отправной пункт, от настоящего использования рабочего места: никаких глобальных запретов «любое действие рядом с зданием».
- Проверить текущие точки завершения построек, включая **автоматическое** завершение последней доставкой, завершение со склада и перестройку; для R02 потребуется единый транзакционный выбор в любом пути.
- **Результат:** короткая карта вмешательств, перечень реальных открытых конфликтов, план тестов.

### Этап 1. Модель исследований и миграция сохранений
- Добавить начальное и сохраняемое состояние всех карточек, без лимита руки, с единым источником истины.
- Селекторы состояния доступны для UI и тестов. Проверять валидные ID, отсутствие повторов, принадлежность, funded only once.
- Для старого сохранения без полей исследований корректно и **однократно** инициализировать R01–R08 как ещё свободные; не сбрасывать строительный прогресс, занятость и цели.
- Подготовить, но **не активировать ложные награды** до завершения полного цикла. Тесты state, сериализации и восстановления.

### Этап 2. Универсальное получение через основное действие
- Реализовать один обработчик получения карты с параметром источника. В нём: собственная активация, свободный рабочий и основное действие, достижимость, ещё доступная карта, валидный источник/рабочее место. Ошибки не тратят рабочего и не резервируют карту.
- Источник Civic Center: используемый городской пункт получения; **не распространять автоматически** лимит «одно здание в год» на целый район. Если для него требуется отдельная городская ячейка/лимит, согласовать точную модель до релиза, не придумывать.
- Источник campus: только завершённое физическое здание; строгая отдельная ячейка на год через actionSpaceOccupancy; свой/чужой посетитель, выплата хозяину +$1 лишь при чужом использовании; несколько копий независимы.
- Тест: R03/R04 забираются даже без больниц/пожарных; второе получение того же ID невозможно; карточку не берёт игрок вне досягаемости или без действия; невозможность повторно занять кампус до сброса года.

### Этап 3. Финансирование — отдельное быстрое действие
- Один обработчик canFundResearch / fundResearch для всех карт, атомарный: валидная фаза/свой ход, статус held у данного игрока, деньги, условия конкретной карты, списание суммы, награда VP и Influence с существующим moveInfluence, изменение статуса и запись лога.
- Проверять R03/R04 **здесь**; нет подходящих учреждений → отказ без изменения денег/статуса/очков; завершённая чужая служба считается; незавершённая — нет.
- Оплаченная карта остаётся открытым технологическим эффектом для **всех**, а не личным бонусом только спонсора.
- Тесты: денег недостаточно, чужая карта, уже оплачено, повторный клик, Influence с занятыми позициями, сохранение/перезагрузка, завершение года, отсутствие расхода основного действия. Много неоплаченных карт у одного игрока допускается.

### Этап 4. Эффекты R01 и R02 — земля и стройка
- **R01:** при финансировании **однократно** применить изменения к текущему Land Value: −1 Marina/Financial/SoMa/Mission/Mission Bay, +1 Pacific Heights/Chinatown, обычные границы 0–6. Не пересчитывать уже уплаченную землю и не срабатывать второй раз.
- **R02:** добавить необязательный выбор **при завершении** подходящей стройки. Достаточно денег → можно заплатить $2, сохранить для конкретной постройки снижение личного вклада У на 1; нет денег → завершение без усиления возможно. Модификатор должен учитываться реальным districtRisk и Фазой II, а не только подсказкой. Сделать единый путь и UI для автоматического завершения доставкой, со склада, через перестройку. Проверить отсутствие двойного списания при отмене/загрузке.
- Если завершение требует выбора, сохранить pending-choice до подтверждения, не теряя материал/worker state.

### Этап 5. Эффекты R03 и R04 — службы и доход
- **R03:** после финансирования собственная Пожароопасность районов от действующих пожарных учреждений снижается на 2 вместо 1; радиус не расширяется. Учесть уже построенные и будущие части, обе разновидности служб по карточке/семейству и взаимодействие с текущими защитами, событиями и лабораторией Фазы II. **Не вычитать один и тот же бонус дважды**.
- **R04:** все подходящие завершённые медицинские учреждения получают +$1 годового Income за учреждение, если есть хотя бы одно завершённое Жилое здание (включая смешанные) в своём или соседнем районе, независимо от владельца. Не умножать на число жилых зданий, проверять при расчёте годового Income по актуальному состоянию, без retroactive payouts.
- Перед реализацией точно сверить соответствие std_fire/firehouse и std_clinic/clinic формулировкам **эффектов**, а не только требованиям финансирования: нельзя тихо потерять стандартные службы из-за буквального текста «часть/клиника». Проверить с утверждённым реестром и обозначить конфликт, если он есть.

### Этап 6. Эффекты R05 и R06 — прогноз и городские цели
- **R05:** настоящая предгенерация, сохранение и публичное отображение **состава поставок следующего года**. Генерация не должна происходить заново при перезагрузке. Важно согласовать с H03 (сокращение морских портов), F03 (портовый пожар), C02 (хищение после пополнения) и другими редакторами запасов, чтобы **прогноз не обещал состав, который потом меняется без понятного основания**. Сохранить прежние распределения ресурсов/баланс, не создавать дополнительные кубики. Тест: два игрока видят одинаковый прогноз, reload не меняет, конец года использует сохранённый прогноз с корректно объяснёнными событийными изменениями. Ограничения по последнему году нет.
- **R06:** при получении новой городской цели доступна опция аванса **+$3 сейчас**, без дополнительного основного действия; затем при успешном отчёте денежная выплата **−$3**, при провале дополнительное **−3 VP**. Только одна **активная** городская цель с авансом на игрока. Реализовать как метаданные конкретной цели с идемпотентным отчётом/провалом, не менять остальные цели. Стартовый рынок и годы учитывать по реальному текущему циклу City Hall.

### Этап 7. Эффекты R07 и R08 — цены и медицина
- **R07:** после финансирования будущие покупки каждого Lumber из логистического узла и у нейтрального поставщика для любого игрока дороже на $1/ед. Считать общую стоимость покупки в существующем deliveryMaterialCost; учесть скидки Procurement/несколько источников/смешанный груз и отображение в UI. **Не повышать цены промышленного источника без отдельного правила**: текущая карта перечисляет node и supplier. Уже купленные материалы, рецепты, риск У не меняются.
- **R08, Фаза I:** стандартный std_clinic стоит за проект **$3 вместо $2 при начале новой стройки** после финансирования. Не менять стоимость иных стандартных проектов, не взимать доплату задним числом с уже начатых строек.
- **R08, Фаза II:** за каждое завершённое и пережившее катастрофу std_clinic/clinic +2 VP владельцу, если **строго соседний** район повреждён или разрушен **землетрясением**. Пожар соседнего района сам по себе не подходит. Одно начисление на учреждение. Через явный адаптер игры к catastrophe-core, а не вычислять из визуальных цветов. Сам симулятор Фазы II отдельный от основного финала; честно обозначить степень интеграции, не заявлять полностью завершённой R08 без тестируемого расчёта Phase II. Учесть известный gap std_fire (issue #43) как зависимость точного пожарного поведения.

### Этап 9. Комплексные регрессии и миграции
