# SF1906 — поэтапный план физических тайлов и переноса в основную игру (24.11.2026)

**Статус: предложенный план разработки, этапы ещё НЕ запущены.** Отправная точка: уже опубликованная `physical-map-lab.html` (PR #237/#239) и ручная [компоновка 79 слотов](PHYSICAL_MAP_LAYOUT_110CM_USER_2026-11-24.json) на поле шириной 1100 мм, тайлы 40×40 мм с пробным зазором 2 мм. Автор игры будет запускать **ровно один этап или подэтап** командами «Приступай к этапу N / NA»; завершённый подэтап = проверенный код + PR / merge в main + актуальные статусы. **Не приступать к следующему без отдельной команды.**

Ключевая договорённость по порядку: **сначала лаборатория и язык тайлов → затем перенос в настоящую игру**, без промежуточной перестройки районов/дорог/портов. Геометрия в JSON уже достаточна; два существенных выступа за прежние контуры North Beach №3 / Financial District №3 пока не исправлять без отдельного дизайнерского решения. Для новых партий предполагается 79 слотов; прежняя основная игра пока имеет 90, по пять в 18 строительных районах.

## Неприкосновенные инварианты

1. **Один игровой движок.** В существующей основной игре объект `state.constructions[]` с уникальным `construction.id`, `projectId`, `districtId`, `playerId`, `status`, `materialsDelivered` остаётся источником истины. Ни лабораторный `placeProject()`, ни `supplyMaterial()` не переносить в настоящую игровую логику. При интеграции добавить к существующему объекту **`slotId`**, а не создавать новый конкурирующий объект или вторую экономику.
2. **Постоянное ID участка.** `slotId = districtId + '-' + number` (например `civic-3`), неизменное независимо от типа здания/владельца и экранных координат. Геометрия — статические `x,y`/масштаб и конфигурация карты; динамические `projectId`/owner/status/инвентарь относятся к состоянию. Один активный объект на участок. Отработать исключение `redeveloped`, `abandoned`, разрушенные здания и перестройку пансиона; **не считать автоматически, что любой статус, кроме complete, освобождает место**.
3. **Сохранения и лимиты по версии карты.** Основной `game-core.js::DISTRICTS` пока содержит `sites:5` и `app.js` при загрузке насильно нормализует `parsed.districts[id].sites=d.sites`. Старую сохранённую партию нельзя автоматически обрезать до двух участков в Chinatown/Marina: выбрать явную версию карты с маршрутом миграции, от которого не потеряются существующие постройки. Отключать старый путь только после проверенной миграции. Старые партии, содержащие >нового лимита объектов, нельзя тихо изменять или уничтожать.
4. **ID здания для других подсистем не меняется.** `actionSpaceOccupancy`, `constructionId` доставки, исследования через кампус, складские остатки, производство, защита, пожары, газетные события, городские цели и связность районов должны продолжать работать без новых самостоятельных реализаций. `districtId` сохраняется авторитетным для требований, логистики и соседства, даже если тайл выступает за графический контур.
5. **Один рендерер и общие визуальные данные.** Лаборатория и основная игра должны вызывать общий слой представления тайла из каталога проекта и реального состояния; не дублировать макеты, словарь иконок и ручные копии текстов в двух HTML. Семантические поля/описатели эффектов лучше парсинга свободного `effect`/ `actionText` с регулярками. Подключение будущих зданий — через данные/реестр и общий обработчик.
6. **Не менять баланс попутно.** Универсальная выплата владельцу +$1 за использование чужим рабочим **в дополнение** к уникальной награде согласована как отдельная будущая правка, но **не внедрять её автоматически с UI тайлов** без аудита старых зданий. Аналогично не менять существующие цены, Income, карты, исследования, награды и ходы только ради нового вида.
7. **Независимость от физического масштаба браузера.** Данные тайла 40 мм и условные координаты SVG отделены от CSS-зума. Лабораторные полиграфические тесты должны проверять реальную читаемость, в том числе трудные 40×40-мм проекты, склад на 5 кубиков и основание рабочего ~14×9 мм.
8. **Тесты каждого этапа.** По `docs/TESTING_POLICY.md`: новые регрессии на реальное поведение, старые тесты не переписывать ради зелёного CI. Сверка текущего HEAD, PR и Pages. В отчёте каждого этапа: изменённые файлы, выполненные тесты, известные ограничения, ссылка на PR, что осталось нетронутым.

- Задать строгий контракт: версия схемы слотов, `slotId`, состояния `under-construction/complete/abandoned/redeveloped`, выделение свободного участка, правило сохранения слота при перестройке, поведение старых сохранений с 90 слотами.

### Этап 1. Вынести геометрию 79 мест в единый статический модуль

- Создать единый валидируемый источник `slotId, districtId, ordinal, x, y`, используя **неизменённую** авторскую раскладку 110 см. Разметка карты только отображает координаты из реестра, а не дублирует координаты в скриптах.
- Проверять ровно 79 уникальных слотов, количество по районам, 40 мм, ≥2 мм между физическими квадратами. Не блокировать допустимые, отдельно осознанные выходы за исторические контуры.
- В лаборатории **строительство по умолчанию**; ручное перемещение спрятать в «Редактор геометрии», не удалять его. Зафиксировать канонический вариант и отдельный редактируемый черновик; безопасность сохранений/сброса.
- **Критерий:** та же авторская карта без сдвига ни одного тайла; тесты импорта старого JSON и новой страницы; действующая основная игра нетронута.

### Этап 2. Развести состояние тестовой застройки и физическую геометрию

- Геометрия одного участка — статична; демо-постройка отдельно хранит `slotId, projectId, owner, materials, status` (в своём пространстве имен; без `constructionId` настоящей партии).
- Сделать чистый преобразователь демо-состояния в «модель представления тайла»; UI перестаёт считывать статус из глобальной переменной в нескольких местах.
- Тестировать создание/освобождение/переворот/сохранение, перезагрузку, импорт legacy JSON с координатами и новую схему. **Не симулировать настоящую экономику.**
- **Критерий:** изменение формата тайла не требует перестройки логики размещения, а правка координат — не приводит к потере тестовых зданий.

### Этап 3. Общий рендерер/модель тайла

- Поддержать одинаковый физический размер, две стороны тайла, сетку размещения текста/иконок, `zoom`, контраст и дополнительные выделенные зоны для владельца, рабочего и ресурсов.
- Подключить новый модуль к лаборатории; UI/интерактив сохраняется. Не переносить в основную игру.
- **Критерий:** никаких дублирующих `drawTile`/карт отдельных зданий на разных страницах, регрессия 79 мест успешна.

### Этап 3A. Производственный аудит формы и сметы — до иконок

**Новая проверенная база (24.11.2026):** автор остановился на [79 шестиугольниках 50 мм](PHYSICAL_MAP_LAYOUT_110CM_HEX50_USER_2026-11-24.json). [Предварительная производственная оценка риска](PHYSICAL_HEX50_MANUFACTURING_RISKS_2026-11-24.md) выявила два дополнительных обязательных вопроса для аудита: **поле 1100×733 мм** может превышать доступный производственный формат отдельных фабрик, а условные складки 4×3 пересекают 32 тайла; для маркировки владельца предложен **один срез вершины** вместо V-выемки. Сравнение ниже — прежний план и **не ограничивает** аудит вариантами только 40 мм. **Этап 3A не завершён**: нет изготовленных образцов и котировок.

**Основание: запрос автора 24.11.2026. Форма тайла ещё НЕ утверждена.** Обязательно сравнивать себестоимость решения вместе с удобством, а не объявлять восьмиугольник готовой новой формой.

- Проверить **четыре физически реальные альтернативы**: (1) квадрат 40×40 мм с условным маркером владельца; (2) обычный шестиугольник в габарите до 40×40 мм с указателем; (3) правильный восьмиугольник в габарите до 40×40 мм с **напечатанным** указателем; (4) восьмиугольник с вырезом/выемкой, открывающей один цвет на поле.
- Для каждой дать геометрический чертёж и число положений, доступную полезную площадь и зону под пять кубиков/рабочего, риск закрывания цветовых меток; проверить, что вариант помещается в **авторские 79 позиции** без правки x/y и без принятия новых границ районов.
- Оценивать **не только цену одного жетона**, но структуру компонентов и полную стоимость экземпляра игры: количество двусторонних листов картона, толщину 1.5/2 мм, фактическую раскладку вырубных контуров на листе, возможное увеличение числа листов/размера коробки, наличие готового штампа у поставщика, индивидуальную стоимость штампа, стоимость наладки/печати/комплектования, тираж, потери материала, срок/стоимость изготовления прототипов, стоимость отдельных маркеров собственности, которые удастся убрать.
- Для расчётов производителя **не путать** физический зазор 2 мм между тайлами **на игровом поле** и технологический зазор между вырубными линиями **на листе**. Несколько производителей указывают **6 мм между резами** и ~3 мм безопасного поля для изображений; окончательные размеры брать из выбранной фабрики. Малую/глубокую выемку не считать гарантированно технологичной: у Boda/LongPack минимальный уникальный край около 3 мм, есть допуски вырубки. Уточнить, позволяет ли фабрика использовать **одну вырубную форму на несколько листов с разными изображениями**.
- Учитывать минимум два класса производства: **прототип/малая серия** (цифровая печать + плоттер/лазер) и **серийное производство** (офсет + штамп). Для тиражных сценариев запросить сравнимые оценки, например 100/500/1000/3000 экземпляров, но **не выдавать внешние публикуемые примеры стоимости оснастки за подтверждённую цену нашей игры**.
- Проверить реальную разницу «обычный восьмиугольник + печатный указатель» против «восьмиугольник с одной физической выемкой»; **для 5 игроков и нейтральных зданий** проверить различимость цветов, планируемую роль 6-го игрока и два запасных положения.
- Результат: отдельная таблица сравнения с **условиями цены, единичными/разовыми расходами, рисками изготовления, качеством читаемости, сохранением 79 слотов** и списком вопросов для запроса смет. Если цены фабрик недоступны — явно пометить «требует котировки», а не придумывать точные цифры.
- **Критерий:** выбранный автором для дальнейшей проработки **кандидат формы**, а не преждевременное необратимое решение. Лишь после этапа 3A приступать к этапу 4 (иконкам), а форму можно окончательно утвердить после практического теста 8A/8Б. Основная игра остаётся неизменной.

### Этап 7A. Сложные здания с рабочими действиями

### Этап 7В. Нестандартные эффекты и автоматическая проверка полноты

- По всему каталогу проверить редкие условия: ограничение 1 раз/год, событие при завершении, переустройство, соседство, выбор на старте/конце года, многосоставные эффекты.

- **Критерий:** отчёт покрытия всех типов проектов; нет тихо пропавших способностей.

### Этап 8A. Проверка обозначения владельца

- Сравнить в визуальном прототипе 2–3 кандидата (цветной угол, рамка/подложка, другой универсальный элемент) на одном и том же тайле 40 мм; никаких именных жетонов здания.

- **Критерий:** владелец виден при занятом рабочем месте и пяти кубиках, без дополнительной ширины игрового поля.

### Этап 8Б. Проверка физического переполнения/читаемости

- Макет фигуры рабочего с основанием ~14×9 мм, пять настоящих кубиков на складе, знаки владельцев разных цветов; тест рядом стоящих зданий и полной застройки 79 мест.

## Группа C — реальное подключение к основной игре (ПОСЛЕ утверждения Группы B)

### Этап 10A. Версионированная вместимость районов и старые партии

- Создать конфигурацию **новой карты на 79 слотов**, чтобы `constructionEligibility()` и UI брали вместимость из выбранной версии карты, а не из нескольких вручную прописанных массивов.
- **Сохранить старым партиям прежнюю карту (18×5)**, не обрезать их до новой. Согласовать точный путь загрузки/миграции; различать legacy/new map version в сохранении.
- Тесты: новый запуск = 79 мест, импорт старого сохранения с >2 зданиями в Chinatown/Marina не теряет здания, перезагрузка не переписывает число мест.
- **Критерий:** один общий обработчик лимита, никакой сломанной истории партии.

### Этап 10Б. Выбор свободного `slotId` при начале строительства

- Расширить `beginConstruction`/проверку доступа параметром слота, валидировать `slotId`/район/занятость и затем **в одном игровом действии** создать стройку с привязкой к участку.
- Оставить старый интерфейс/вызовы совместимыми там, где нужна legacy-карта. Не дублировать расход основного действия, цену земли, портфель, выбор рабочего и рейсы.
- Тесты: два игрока не строят в одном слоте, свободный слот действительно занимает одно здание; нельзя строить в другом районе через подложный `slotId`; нет денег/рабочего = объект не создаётся.
- **Критерий:** `constructionId` прежний, `slotId` новый; один источник правды о занятости.

### Этап 10В. Перестройка, разрушения, закрытие и миграции

- Привязать `redevelopedFrom`/замену вагонного пансиона к **тому же участку**; обновить освобождение мест и правила для abandoned/redeveloped согласно действующему движку.
- Поддержать сохранение/загрузку и idempotent-миграции без временного двойного владения участком.
- Тесты крайних случаев: перестройка в полном районе, закрытие на пороге года, пожар/разрушение, действия к уничтоженному зданию, повторная загрузка.

### Этап 11A. Реальный рендеринг 79 слотов на главной городской карте

- Один квадрат ↔ конкретный `slotId` ↔ (опционально) один `constructionId`, автоматическое обновление при доставке/завершении; старый способ рисования поддержать для legacy-партий, пока требуется.
- **Критерий:** настоящая партия корректно показывает начало строительства и переворот на реальную готовую сторону без изменения расчётов.

### Этап 11Б. Интерактивность строительства и рабочих
