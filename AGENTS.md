# San Francisco 1906 — инструкции для AI-ассистентов

Назначение: обеспечить непрерывность проектирования между чатами и безопасную работу с текущим кодом. Этот файл НЕ заменяет документы правил.

## Начало новой сессии (обязательно)

1. Прочитать `docs/PROJECT_STATUS.md` (текущее состояние и карта документов).
2. Прочитать `docs/CORE_RULES.md` (базовый игровой цикл, с оговорками о статусе).
3. Прочитать `docs/REJECTED_IDEAS.md` (чего не предлагать повторно), **`docs/DESIGN_FEEDBACK.md`** (что пользователю не понравилось и почему, даже если не было окончательного отказа), последние записи `docs/DECISION_LOG.md`; для спорных/старых тем также посмотреть `docs/CONTEXT_AUDIT_2026-10-24.md` (подтверждённые разрывы и источники).
4. Затем читать только профильные документы для текущей задачи: `docs/buildings-master-registry.md`, `docs/card-rules-draft.md`, `docs/deferred-partnerships.md`, `docs/phase2-earthquake-fire-v01.md` и/или код.
5. При начале задачи уточнить по файлам, что именно **реализовано**, что **утверждено к реализации**, а что **пока только концепт**. Не тратить контекст на полное чтение всего репозитория без необходимости.

У ChatGPT файлы GitHub не читаются автоматически только из-за наличия ссылки или этого AGENTS.md: в начале нового чата явно запросить их чтение. Codex/другой агент может использовать этот файл в соответствии со своими возможностями.

## Статусы — не смешивать

- **Внедрено в main**: код действительно существует в текущей main. **Протестировано** указывать только с реально подтверждёнными результатами тестов.
- **Утверждено для теста / дизайна**: пользователь одобрил решение, но оно может отсутствовать в движке; числа могут быть предварительными.
- **Концепция / обсуждается**: идея без окончательного согласования, не переносить в активные правила.
- **Отложено**: к идее можно вернуться после указанной зависимости/этапа; это не отказ навсегда.
- **Отклонено / заменено**: не предлагать исходную версию заново без новой причины или прямой просьбы пользователя.
- **Требует сверки**: источники расходятся либо нет подтверждения. Не заполнять пробелы догадкой.

## Приоритет доказательств при расхождениях

1. Для **новых дизайнерских решений**: последнее явное решение пользователя в контексте > более раннее решение или предложение. Без подтверждения нельзя считать выбор утверждённым.
2. Для **того, что реально работает**: код текущего main + тесты + подтверждённый merged PR; дизайн-документы не доказывают работоспособность.
3. Для **реестра утверждений**: профильный актуальный реестр и `docs/DECISION_LOG.md`; датированные проектные заметки — исторические снимки, иногда устаревшие.
4. Если код и утверждённое правило расходятся, не выбирать удобную трактовку: пометить **разрыв реализации** и предложить отдельно исправить код.
5. Нельзя ссылаться на несуществующие чаты, PR, тесты и исследования. Источник решения — ссылка на файл/PR или явно отмеченная дата разговорного решения.

## Как проектируем

- Обсуждать механики критически: преимущества, слабые места, злоупотребления, историческая достоверность, сложность и баланс.
- При обсуждении новых зданий сверяться с существующими способностями: не дублировать эффект другими названиями. Особое внимание дисбалансу западных районов, востребованности Lumber и чрезмерному спросу на Masonry.
- Не делать кодовую реализацию только потому, что предложена концепция. Отдельно различать «утвердили эффект», «согласовали числа», «внедрили» и «проверили на мобильном».
- Не обходить базовый маршрутный граф, действующие правила доставки/вместимости и локальное перемещение представителей без отдельного решения.
- **Зафиксированное решение 24.10.2026:** стандартный пожарный пост `std_fire` действует только в районе постройки **в обеих фазах**, без соседней защиты. Полноценная рыночная `firehouse` — отдельная карта; строительный доступ к ней в соседнем районе не является автоматическим снижением риска пожара. Не считать отсутствие поддержки `std_fire` в симуляторе Фазы II новым правилом: это незавершённая реализация.
- После явного утверждения пользователя обновлять профильный реестр, `docs/DECISION_LOG.md`, при необходимости `docs/PROJECT_STATUS.md`; **окончательно отвергнутые варианты** — в `docs/REJECTED_IDEAS.md`, **содержательную критику и пожелания к предложенным вариантам** — в `docs/DESIGN_FEEDBACK.md`. Не ждать отдельного напоминания «запиши это в GitHub». Сведения о реализации меняются только после подтверждённого merge/проверки main.
- Не дублировать полный текст карточек во многих документах. Документы сводки содержат ссылку на первичный реестр/код и короткий статус.

## Как сохранять возражения во время обычного обсуждения

1. Если пользователь говорит **«не нравится» и объясняет почему**, зафиксировать обратную связь: точный вариант, причину из слов пользователя, критерий следующей итерации и дату. **Не** объявлять это категорическим запретом всей категории и не придумывать невысказанные причины. Место: `docs/DESIGN_FEEDBACK.md`.
2. Если пользователь прямо **отверг конкретный эффект/вариант** («не используем», «отбрасываем», «это решение больше не предлагать»), занести его с причиной и заменой (если названа) в `docs/REJECTED_IDEAS.md`. Если причина не названа, указать «причина не указана», а не выдумывать.
3. Если пользователь **утвердил** идею или правку, записать в профильный реестр и `docs/DECISION_LOG.md`, но не приписывать реализации, пока нет кода/merge.
4. **Не откладывать фиксацию до переполнения чата:** во время небольшого обсуждения можно собрать 2–3 замечания, затем сохранить в GitHub **в конце этого тематического мини-цикла**, перед переходом к другой категории или сразу после окончательного отказа. Не делать отдельный PR для каждой мелкой реплики; группировать документационные изменения.
5. Использовать отдельную ветку/PR, проверить корректность Markdown и ссылок. Для чисто документационного согласованного обновления можно объединять после проверки; **открытый PR не считается записью в main**. В ответе кратко сообщать, какие конкретно записи сохранены и где, **только после успешной записи**. Если нет доступа GitHub, прямо назвать записи несохранёнными и показать текст для последующего переноса.
6. При новом чате проверить **открытые документационные PR** и при необходимости их завершить, чтобы не потерять замечания, записанные не в main. Когда пользователь пересматривает решение, сохранить историю смены статуса, а не стирать её.

## Рабочий цикл изменения кода

1. Проверить текущую main, выяснить требуемую механику, имеющиеся тесты и последствия для сохранений.
2. Сделать изолированную ветку/PR; не подменять ранее утверждённые механики собственными поправками.
3. Проверить `npm run test:core`; для UI — `npm run test:e2e` и отдельно мобильные размеры **390×844** и **932×430**, если доступна среда запуска.
4. Если тесты/браузер не запускались — так и указать, не писать «проверено».
5. Обновить реестр, status, журнал решений в том же PR, где меняется механика. Не сливать крупные несогласованные дизайнерские изменения.
